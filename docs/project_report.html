Abstract

The DriveEase Vehicle Rental Management System is a commercial fleet reservation and tracking platform built to automate the core operations of a rental company. Traditional rental services struggle with operational delays, inaccurate manual damage estimations, unrecorded overdue fines, and invoice inconsistencies. This project presents a relational database model that resolves these challenges.

The architecture utilizes a Node.js and Express backend to expose REST APIs, connected to a normalized MySQL 8.0 relational database. On the frontend, a responsive, minimalist dashboard was built using Vanilla HTML5, CSS3, and JavaScript.

To ensure database constraints and data integrity, the system implements triggers for state monitoring, views for reporting aggregations, and **transaction-safe stored procedures** for booking checks and vehicle check-ins. The system is equipped with an integrated Chart.js dashboard for analytics and print media templates that generate receipt invoices instantly. It serves as a comprehensive, end-to-end showcase of modern database design and full-stack software development.

Chapter 1: Introduction

1.1 Project Objective

The objective of the DriveEase platform is to automate booking, billing, and inspection records. The application aims to replace insecure spreadsheets with an ACID-compliant SQL engine. It enables fleet operators to log cars, manage customers, checkout vehicles, calculate late fees, assess damages, and track lifetime earnings.

1.2 Drawbacks of Manual Ledgers

Manual car rental tracking introduces several critical vulnerabilities:

  • Double Bookings: No concurrency controls exist to prevent assigning the same car to two customers simultaneously.
  • Unrecorded Overdue Fines: Returning officers fail to calculate exact late durations (in hours) and miss collecting late charges.
  • Corrupted Audits: Manual arithmetic errors in adding security deposits, state sales taxes (12%), and discounts lead to financial leaks.
  • No Inspection Trails: Scrapes and dent details are logged on paper slips that are easily misplaced, letting renters return damaged cars without penalty.

1.3 Proposed System Advantages

The proposed DriveEase system addresses these flaws using database-level automation:

  • State Lock Triggers: Triggers ensure that when a booking is created, the vehicle status is locked to `'rented'` instantly.
  • Stored Procedure Calculations: Standardized tax calculations and late fee estimators ensure consistency.
  • Transactional Integrity: Operations are grouped within SQL transactions (COMMIT/ROLLBACK) so that a failure in billing reverses all status modifications, keeping tables clean.

Chapter 3: System Design

3.1 Entity-Relationship (ER) Diagram

The entity-relationship model consists of strong entities mapping the business logic:

  • Admins: System operators managing inventory and checkouts.
  • Customers: Renters with driver profiles.
  • Vehicles: The physical rental fleet.
  • Categories: Pricing specifications (daily rates, security deposits, late fees).
  • Rentals: Active and past booking events.
  • Invoices: Financial billing sheets generated for rentals.
  • Payments: Ledger transactions.
  • Returns: Return inspections, odometer readings, and damage details.

3.2 Schema Diagram

The schema defines clear foreign key constraints:

  • vehicles.category_id references categories.category_id (Many-to-One).
  • rentals.customer_id references customers.customer_id (Many-to-One).
  • rentals.vehicle_id references vehicles.vehicle_id (Many-to-One).
  • invoices.rental_id references rentals.rental_id (One-to-One).
  • returns.rental_id references rentals.rental_id (One-to-One).

3.3 Database Normalization

The schema was designed up to Third Normal Form (3NF) to eliminate redundancy:

  • First Normal Form (1NF): All values are atomic (e.g., separating first_name and last_name; using auto-increment integer primary keys).
  • Second Normal Form (2NF): No partial dependencies exist. All columns in vehicles depend fully on vehicle_id.
  • Third Normal Form (3NF): Transitive dependencies are eliminated. Rather than storing the daily rate inside the vehicles table (which would create a transitive dependency: Vehicle ➔ Category ➔ Daily Rate), a separate categories table was created. The vehicle table only references category_id, separating pricing from physical inventory.

Chapter 4: Implementation

4.1 MySQL Table Structures (DDL)

Below are snippets of the tables, primary keys, and constraints defined in the schema: 

CREATE TABLE categories (
    category_id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) UNIQUE NOT NULL,
    daily_rate DECIMAL(10,2) NOT NULL CHECK (daily_rate >= 0),
    late_fee_per_hour DECIMAL(10,2) NOT NULL CHECK (late_fee_per_hour >= 0),
    deposit_amount DECIMAL(10,2) NOT NULL CHECK (deposit_amount >= 0)
);

CREATE TABLE vehicles (
    vehicle_id INT AUTO_INCREMENT PRIMARY KEY,
    make VARCHAR(50) NOT NULL,
    model VARCHAR(50) NOT NULL,
    license_plate VARCHAR(20) UNIQUE NOT NULL,
    category_id INT NOT NULL,
    status VARCHAR(20) DEFAULT 'available' CHECK (status IN ('available', 'rented', 'maintenance', 'retired')),
    mileage INT NOT NULL DEFAULT 0,
    FOREIGN KEY (category_id) REFERENCES categories(category_id)
);

4.2 Database Logic

Triggers

Triggers automate state updates. For example, tg_after_return_insert updates vehicle mileage and sets status to available or maintenance: 

CREATE TRIGGER tg_after_return_insert
AFTER INSERT ON returns
FOR EACH ROW
BEGIN
    DECLARE v_vehicle_id INT;
    SELECT vehicle_id INTO v_vehicle_id FROM rentals WHERE rental_id = NEW.rental_id;
    
    IF NEW.damage_notes IS NOT NULL AND CHAR_LENGTH(TRIM(NEW.damage_notes)) > 0 THEN
        UPDATE vehicles SET status = 'maintenance', mileage = NEW.mileage_in WHERE vehicle_id = v_vehicle_id;
    ELSE
        UPDATE vehicles SET status = 'available', mileage = NEW.mileage_in WHERE vehicle_id = v_vehicle_id;
    END IF;
    
    UPDATE rentals SET status = 'completed', actual_return_date = NEW.return_date WHERE rental_id = NEW.rental_id;
END;

4.3 Backend API Routers

The server routes HTTP requests and queries MySQL using connection pools:

  • POST /api/auth/login: Validates credentials and returns JWT.
  • GET /api/vehicles: Lists vehicles with pagination and search filters.
  • POST /api/rentals/book: Initiates booking by executing sp_create_booking.
  • POST /api/rentals/return: Processes returns by executing sp_process_return.

4.4 Frontend Viewports Layout

The interface is built as a single-page application (SPA). Content views are wrapped in divs (like view-dashboard, view-vehicles) that toggle visibility dynamically.

We integrated **Chart.js** on the analytics page to render:

  • Revenue Share: A Doughnut chart showing earnings per vehicle category.
  • Booking Metrics: A Bar chart showing the active rental days of the top vehicles.
