# DBMS Mini-Project Viva Q&A

This guide contains frequently asked questions during DBMS project reviews, along with practical, technically solid answers based on the **Vehicle Rental Management System**.

---

### Q1: What is the normalization level of this database? Explain with examples.
**Answer:** The database is normalized up to **3rd Normal Form (3NF)**:
*   **1st Normal Form (1NF):** Every cell contains atomic (single-valued) values, and there are no repeating groups. For instance, customer names are separated into `first_name` and `last_name`, and individual rentals have unique integer primary keys.
*   **2nd Normal Form (2NF):** It is in 1NF and all non-key attributes are fully dependent on the primary key (no partial dependencies). In the `vehicles` table, details like `make`, `model`, and `mileage` depend entirely on the `vehicle_id`.
*   **3rd Normal Form (3NF):** It is in 2NF and has no transitive dependencies (non-prime attributes depending on other non-prime attributes). Instead of storing pricing details directly inside the `vehicles` table, we created a separate `categories` table. The vehicle table references `category_id`, eliminating transitive dependency (i.e., Vehicle ➔ Category ➔ Daily Rate).

### Q2: Why did you use Stored Procedures? What advantage do they have over normal query execution?
**Answer:** Stored Procedures were used for complex transactions (`sp_create_booking` and `sp_process_return`):
1.  **ACID compliance & Transaction Safety:** Booking a car requires checking vehicle status, verifying the customer, writing the rental, and generating the invoice. If any step fails, the entire transaction is rolled back (`ROLLBACK`) preventing corrupt data states.
2.  **Performance & Reduced Latency:** Instead of executing 4 or 5 separate network queries between the Node.js server and the MySQL server, a single `CALL` statement is issued. The database processes all commands internally.
3.  **Encapsulation of Business Logic:** The formulas for calculating rental costs, tax margins, and late fees are kept directly in the database layer. This ensures that any frontend or secondary API connecting to the database will calculate rates identically.

### Q3: Explain the database Triggers you implemented and their purposes.
**Answer:** We implemented two automatic triggers:
1.  `tg_after_rental_insert` (**AFTER INSERT ON rentals**):
    *   *Purpose:* Automatically updates the rented vehicle's status to `'rented'` when a new rental is created.
    *   *Benefit:* Eliminates manual updates in the application layer. The database ensures that a vehicle is marked as occupied immediately upon checkout.
2.  `tg_after_return_insert` (**AFTER INSERT ON returns**):
    *   *Purpose:* Fires when a vehicle is checked back in. It marks the rental status as `'completed'`, sets the actual return date, updates the car's current mileage, and sets the vehicle status to either `'available'` or `'maintenance'` (if damage notes are reported).

### Q4: What is a Database View? Why did you use them here?
**Answer:** A view is a virtual table representing the output of a pre-compiled SQL query. We created two views:
1.  `vw_rental_details`: Joins tables (`rentals`, `customers`, `vehicles`, `categories`, `invoices`, `returns`) into a unified dataset.
    *   *Why:* Simplifies backend code. Instead of writing massive SQL JOIN queries inside the Express routers, we run a clean `SELECT * FROM vw_rental_details WHERE status = 'active'`.
2.  `vw_vehicle_utilization`: Aggregates active rental days, booking counts, and lifetime revenue generated by each car.
    *   *Why:* Calculates business intelligence statistics instantly.

### Q5: What indices did you define, and why are they necessary?
**Answer:** Indices are defined using `CREATE INDEX` on foreign keys and columns frequently used in search filters:
*   `idx_vehicle_status` on `vehicles(status)`
*   `idx_rental_status` on `rentals(status)`
*   `idx_customer_license` on `customers(license_number)`
*   *Why:* These columns are repeatedly used in `WHERE` clauses (e.g., finding available vehicles, searching for driving licenses). By creating B-Tree indexes, MySQL can locate records in logarithmic time $O(\log N)$ instead of scanning the entire table $O(N)$, which is critical as the dataset grows.

### Q6: How does the application handle database connectivity failures?
**Answer:** The system uses a **Dual-Mode Architecture**:
1.  During startup, `backend/config/db.js` attempts to establish a connection pool to the configured MySQL instance.
2.  If the connection fails (e.g., MySQL is offline, or credentials are unconfigured), the system intercepts the error, prints a prominent diagnostic console log, and falls back to a **fully functioning In-Memory Mock Database**.
3.  The frontend is also equipped with a client-side mockup fallback. If the backend server goes down, the browser utilizes `localStorage` to save vehicles, register customers, calculate late fees, and compile invoices locally. This ensures that the application is immediately testable out-of-the-box.

### Q7: What is the difference between an INNER JOIN and a LEFT JOIN? Give examples from your project.
**Answer:**
*   **INNER JOIN:** Returns records only when there is a match in both tables.
    *   *Example:* `SELECT * FROM vehicles JOIN categories ON vehicles.category_id = categories.category_id`. This only returns vehicles that have a valid category.
*   **LEFT JOIN:** Returns all records from the left (first) table, and the matched records from the right (second) table. If there is no match, it returns `NULL` for the right side.
    *   *Example:* In `vw_rental_details`, we use `LEFT JOIN returns ON rentals.rental_id = returns.rental_id`. This is crucial because active rentals do not have return records yet, and an INNER JOIN would hide all active rentals! The LEFT JOIN allows us to see both active and completed rentals.
